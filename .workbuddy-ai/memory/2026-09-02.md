## View-folder naming bug fix (later same day)
- Symptom: `InvalidArgumentException — View [pages.batchtiket.table] not found` when opening the batch-tiket module.
- Root cause: `ControllerTrait::template()` derives the view folder as `strtolower(str_replace('Controller','', $className))` → **no separators** (e.g. `BatchTiketController` → `pages.batchtiket`). The WP subagents created 9 multi-word module folders using separators (`batch_tiket`, `suku-cadang`, `stok-suku-cadang`, `pergerakan-stok`, `pesanan-pembelian`, `template-service`, `jadwal-service`, `riwayat-service`, `penjualan-aset`), which never matched the auto-derived name.
- Fix: renamed those 9 folders to the concatenated-lowercase form the trait expects (`batchtiket`, `sukucadang`, `stoksukucadang`, `pergerakanstok`, `pesananpembelian`, `templateservice`, `jadwalservice`, `riwayatservice`, `penjualanaset`). No explicit `pages.<old>` references existed in blades/controllers. Verified via `View::exists()` that all 29 modules' `.table` and `.form` views resolve (NONE missing). Cleared view + config cache.
- Rule of thumb: AMS view folders MUST equal the controller class name minus `Controller`, lowercased, with NO separators. The route slug (e.g. `batch-tiket`) is independent of the view folder name.
- **CORRECTION (same day, 2nd error):** the earlier "all 29 resolve" claim was FALSE — the verification loop hand-typed `dafartunggu` (a typo) as the expected name, so it passed against the typo'd folder. The real `DaftarTungguController` derives `daftartunggu` (with the **t** in "daftar"), but the folder was `dafartunggu` (missing t) → `View [pages.daftartunggu.table] not found`. Renamed `dafartunggu` → `daftartunggu`. No references to break. Re-verified with an AUTHORITATIVE bash loop that derives the expected folder from each controller's actual `class XController` declaration and checks disk — now all 29 AMS controllers resolve (only dashboard/profile/websitesetting legitimately excluded: they return explicit views like `dashboard`/`settings`, not `pages/{module}`).
- **Lesson:** never hand-list expected names when verifying — always derive the expected folder from the controller class name programmatically, otherwise a typo in the expectation masks the bug.
- **Stale dev-server realpath cache (3rd error, `pesananpembelian`):** after renaming view folders while `php artisan serve` (background task) was RUNNING, the long-lived PHP process cached negative `realpath()` results for the new view paths. The files existed on disk and `View::exists()` returned FOUND in a fresh `tinker` process, but the live server kept throwing `View [pages.X.table] not found`. Fix: stop the dev server, `php artisan view:clear && config:clear && route:clear && optimize:clear` (+ remove `bootstrap/cache/*.php`), then restart `php artisan serve --host=0.0.0.0 --port=8000` (new task `ZLO1MR`). After restart all 29 modules resolve. **Workflow rule:** whenever view folders/files are moved/renamed, RESTART the running dev server (or flush realpath cache) — don't just rely on on-disk existence; the live process won't see renames until restart.

- **Faithful view verification (don't trust bare `view()` / tinker):** rendering `view('pages.X.table')` directly (or in tinker) throws false errors — `$fields` undefined (controller's `getTable()` passes it via `getFields()`/`share()`) and `getController()/getAction() on null` (no route context in tinker). Correct test: add a TEMP unauthenticated route that calls the REAL controller `getTable(app(GeneralRequest::class))` and `->render()`, then curl it. All 29 AMS modules render 200 this way. REMOVE the temp route afterward (it exposes views unauthenticated) and restart.

Disk + tinker both FOUND the file (`sukucadang/table.blade.php` exists, 4719 bytes; `View::exists` → FOUND). Fix: `taskkill /F /PID <listener-from-netstat>` (NOT just TaskStop), confirm `netstat … :8000 … LISTENING` is GONE, THEN start fresh. ## Authenticated render smoke-test harness (reusable, better than tinker)
- tinker/`view()` gives false errors (`$fields` undefined, `getController() on null`). A temp route works but must be removed. **Best:** a standalone script that boots the app, sets the user directly, and runs the HTTP kernel:
  ```php
  require __DIR__.'/vendor/autoload.php';
  $app = require_once __DIR__.'/bootstrap/app.php';
  $app->make(Illuminate\Contracts\Console\Kernel::class)->bootstrap();
  Auth::guard('web')->setUser(App\Models\User::first());
  $k = $app->make(Illuminate\Contracts\Http\Kernel::class);
  foreach ($uris as $uri) {
      $r = Illuminate\Http\Request::create($uri,'GET');
      $app->instance('request',$r);
      Facade::clearResolvedInstance('request');
      echo $uri.' -> '.$k->handle($r)->getStatusCode();
  }
  ```
  Renders real authenticated pages (200 = OK) with no temp route residue. Delete the script after use.
